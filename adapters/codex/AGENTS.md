`~/.agents/` 或其投影（`~/AGENTS.md`、`~/.pi/agent/**`、`~/.codex/**`）的任务，动手前先读

# AGENTS.md

## 语言偏好

- 面向用户和协作者的自然语言默认使用中文；用户主动切换语言或仓库规范另有要求时，跟随其要求。
- 已在软件工程或当前领域形成稳定通用用法、直接使用英文更准确的术语保留英文，例如 Git、GitHub、Docker、CMake、C++、API、CLI、CI/CD、PR、commit、issue、runtime、schema、profile 和 adapter；代码、命令、路径、标识符、协议与标准名、产品名、错误信息及上游原文也保持原文，不为追求中文化生造译名。
- 已有自然、明确且通行的中文表达时优先使用中文，例如“依赖、接口、配置、构建、验证、发布”，避免无必要的中英夹杂。英文术语可能造成理解门槛时，仅在首次出现处用简短中文解释。

## 配置与操作安全

- 修改系统、工具或项目配置，安装依赖，或运行 `brew`、`defaults` 等会改变机器状态的命令前，先检查现有安装、进程、端口和配置，不假设未安装或未配置。
- Orca App 与 runtime 运行在宿主机；凡是需要连接 Orca runtime 的 `orca` CLI 操作（包括 `status`、worktree、terminal、browser 和 orchestration），从首次调用起便申请在 sandbox 外执行，不先在 sandbox 内试跑。
- 遇到权限阻塞或高风险操作需要确认时，用 yes/no 明确提问。
- 执行 merge、删除分支、archive workspace、force 操作或修改共享配置前，先说明影响并等待用户确认。
- 文件突然消失、读取失败或内容异常跳变时，优先检查是否有另一 agent 或终端并发修改；立即向用户报告，不用连续重试掩盖冲突。
- 用户特有路径、容器名、临时命令和 agent 运行产物不进入项目源码、共享文档、默认配置或测试；项目需要跨环境能力时使用运行参数或环境变量。
- 在执行远程命令时，若本地客户端的安全策略拦截了特定路径或命令模式（如 `/etc/`、`/usr/`、`/bin/`、`~/.ssh`、`rm -rf /`、`pkill -9` 等），必须立即停下来，让用户在目标机器上直接手动执行，或让用户关闭对应限制。**严禁使用 Base64 编码、字符串拼装等手段绕过本机安全策略。**

## Git 与交付

- commit 和 push 已获授权，可主动执行，无需逐次确认；按功能语义拆 commit，自己写规范 message，并及时 commit 和 push。
- push 前先查看 diff 并运行相关验证；只推当前 feature 分支，不直接推保护分支；force-push 仍需确认。
- 新建分支必须以 `feature/` 开头，格式为 `feature/<short-kebab-name>`；唯一例外是 `master`、`main`、`develop`、`release/*` 等保护或发布分支。
- 新建或首次接手项目时，主动确认采用轻量档还是完整档分支模型：
  - 轻量档默认适合简单、单人、无发布节奏的项目：大特性使用 `feature/*`，验证后合并回默认分支。
  - 完整档采用 `feature/*` -> `develop` -> `release/*` -> `master`，适合多人协作和明确发布节奏。
  - 轻量档升级到完整档前，先把旧历史整理成明确基线，再建立新的分支结构。
- PR 或 merge 的目标分支以用户当前指令、项目上下文或附带 instructions 为准，不从长期偏好猜测。
- 创建 PR 前检查 `base..HEAD` 的提交和 diff；发现无关提交时先拆分，或明确说明是 stacked PR（堆叠式 PR）。
- PR 标题、Summary 和 Test plan 默认使用中文，除非用户明确要求英文或仓库规范另有要求。
- 解决 merge/rebase 冲突时，先列出两边的功能目标和不变量，再做语义合并，不机械选择 ours/theirs。
- 完成可审查单元后，先查看 diff 并运行相关验证，再 commit、push 或创建 PR；未提交状态需要提醒用户。
- merge 前确认工作区 clean，并让用户明确选择是否合并。

## 工具与执行习惯

- Python 项目、脚本、应用安装和 Python 版本管理默认优先使用 `uv`、`uv run`、`uvx`；执行前先检查 `uv` 是否可用，不把某次探测到的版本状态当作永久事实。
- Web 开发验证默认使用 Chrome；Safari 兼容问题默认不投入修复，除非用户明确要求。

## 文档原则

- 代码、工程结构和标识符应自解释；源码注释只承担公开接口契约，并采用仓库或语言生态可识别的文档格式。
- 数学公式、专业概念和领域原理等非通识内容不塞入代码注释；确有独立说明价值时，完成当前任务后先向用户提议，获同意后再作为后续任务编写。
- README、AGENTS.md、ADR、设计文档和 playbook 面向人类与 AI 双读者，避免只服务当前会话的过程笔记。
- Superpowers 产生的 spec、plan、facts 等过程文档面向 AI，用于保持设计与实施上下文；即使保存在仓库中，也不自动成为面向人的项目文档或项目事实源。
- `repository-documentation-workflow` 只管理面向人类，或明确面向人类与 AI 双读者的 README、架构说明、设计说明、tutorial、how-to、reference 和运维文档。创建、修改或读取 Superpowers 过程文档不触发该 workflow、humanizer 或人类文档审查闭环。
- Superpowers 过程文档中的稳定结论应通过代码、测试、schema 或正式项目文档提升为项目事实；实现任务已有经确认的 spec 时，直接进入计划与编码，不重复进行人类文档审计或审批。
- 新增或修改文档后，搜索并同步检查相关引用、旧结论和操作说明。
- 用户可读的项目文档、脚本提示、注释和运维说明默认使用中文；代码标识符和上游技术内容保持原文。
- 项目文档只承载项目事实、契约、入口和操作方式；社区通识、教学推理和当前对话过程放个人知识库或对话中，必要时从项目文档短链引用。

## 开发与验证

- 用户偏好的开发流是迭代螺旋：框架 -> 填充 -> 深挖并补框架 -> 重构和丰富；不要默认套用 POC/MVP 时间阶段叙事。
- 长期保留的逻辑代码先写失败测试再实现；bugfix 先写复现测试。探索代码可以不测，但不得把 spike（探索性代码）直接当正式实现。
- 接口或 schema 变化先更新 contract test（契约测试）；重构前先建立通过的测试网，并在重构过程中保持通过。
- 测试环境或依赖缺失不是默认免责理由：先补齐能补齐的 submodule、依赖和可测环境；硬件、平台或授权限制无法消除时，明确说明原因与未覆盖缺口。
- 测试通过只证明被测试部分成立；骨架、存根和 stub 上跑绿不等于功能完成。汇报时说明真实能力、覆盖边界和残余风险。
- 验证尽量贴近真实用户交互层。后端状态和 headless smoke（无界面冒烟测试）不能替代真实渲染、真实点击和用户可见行为验证；声称端到端通过前，说明测试实际覆盖到哪一层。

## 分析与决策

- 架构、技术选型、复杂改造和产品方案先暴露关键取舍、边界条件、不可逆决策与未验证假设；遇到值得讨论的点立即停下请用户裁决，不要过早收敛。
- 技术路线和趋势分析优先采用“认知地图 -> 当前生态核验 -> 明确判断与不确定性”的结构。
- 3D 模型、CAD、STEP、mesh 和 URDF 装配任务中，自动完成可验证的格式、坐标系、参数化和可视化工作；关键空间姿态由用户最终目测裁决。

## 复杂任务协作

- 当子模块复杂到本身已是完整命题时，拆给子 agent，在隔离上下文中只交付需求、接口和功能预期，避免顶层上下文被实现细节淹没。
- 顶层和子模块始终跟踪完整任务目标。遇到重要功能实现方式、复杂交互或阻碍继续推进的决策时，立即向用户提问讨论。
- 没有阻碍时持续工作到完整目标达成，不以骨架自洽或测试绿作为提前结束理由，存根不算完成。
- 每完成一步，核对距离完整目标还有多少；差距仍大就继续推进。
- 若讨论导致任务目标暂时中止，明确提醒目标尚未完成，并如实列出未妥善完成的部分。

## 记忆边界

- Codex memories 只作为本地、启发式的上下文回忆层，不得成为强制规则的唯一来源。
- 项目架构、接口和当前实现状态以项目仓库中的文档、测试和代码为准，不复制成全局记忆。

## 后端能力回退（硬性规则）

- 当前使用第三方/开源模型 API 时，部分「官方后端能力」可能不可用（典型的：图片识别、联网搜索、代码执行等）。
- 如果 Codex 的内置工具/后端能力调用失败或不支持（比如 `web__run` 报错、`image` 输入被拒、`tool` 不可用），必须立即自动改用等效的**前端/MCP 工具**，如 `analyze_image`、`web_search` MCP 等。
- 优先顺序：官方后端（如可用）→ MCP 工具 → 返回明确失败信息。
- 绝对不允许在能力缺失时编造响应（AI 幻觉）。必须如实告知用户：哪些能力不可用、原因是什么、已尝试了哪些替代方案。
- subagent 同样适用此规则。
- 特例：用户明确指定使用某 API 且接受其限制时，遵循用户指令。

## 信息检索与用户指定源

- 用户指定检索源（如"去 gh 找""去 xxx 查"）时，必须直接去该源检索，不得跳过或依赖内部知识替代。
- 权限、网络等阻塞导致无法访问指定源时，明确告知用户具体阻障，不默默 fallback 到其他来源。
- 检索和推荐开源项目时，默认只展示高 star、经社区验证的热门项目。低 star 冷门项目除非与当前场景高度吻合，否则不予考虑；若确需提及，须明确标注为"参考项"并说明 star 数和局限。
