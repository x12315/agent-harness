# 自解释代码与接口文档

## 自解释工程结构

让工程结构和标识符直接表达领域含义、角色、边界与作用域。检查当前任务涉及的目录、模块、包、命名空间、文件、类型、函数、方法、变量、参数和配置标识符；采用准确、具体且符合当前语言和仓库惯例的名称。

当相关代码仍需依靠说明性注释才能表达用途时，优先在当前任务范围内改进命名、类型、职责划分或模块边界。

## 源码注释

将源码中的人类可读说明集中在模块公开接口及其公开成员的契约注释中。让私有实现、局部逻辑和普通数据流通过结构与命名完成解释。

修改相关代码时，同步清理已经失效、重复代码含义或可由命名与结构取代的注释。保持改动范围聚焦，不清理任务无关区域。

## 接口注释

为模块对外暴露的函数、类型、类、常量及公开成员编写接口注释。

先检查仓库已有的文档生成工具、配置和既有格式；存在约定时保持一致，否则使用当前语言通行且可被文档工具识别的格式。

接口注释只提供外部调用者需要的契约信息：用途，以及签名无法充分表达的输入、输出、错误、约束或副作用。实现过程、一般知识、数学推导、专业概念和领域原理不进入接口注释。

## 概念文档提议

如果实现明显依赖大量数学公式、专业概念或领域原理才能被正确理解和维护，不把说明塞入源码或接口注释。完成当前任务后，向用户提议将相关知识作为后续独立文档；获得明确同意后，再在下一流程确定范围并编写。没有明显文档需求时不提议。

## 完成检查

交付前检查本次任务涉及的全部工程路径与标识符是否自解释、全部公开接口是否具有工具可识别的契约注释，以及源码中是否仍存在由注释代替命名或结构的问题。需要概念文档时，只提出后续任务，不在当前任务中创建。
